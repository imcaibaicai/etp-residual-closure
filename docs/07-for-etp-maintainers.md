# 07 — If this were to become an ETP contribution

> **中文摘要**
> 本文说明若要把它做成 ETP 正式贡献需要什么：作者侧形式化、全量构建、CI、维护者审查——本项目一件都没做，所以它现在不是贡献。
> 按 ETP 自己的布局，形式化形状是「一张见证表一个 `Magma (Fin n)` 实例 + 一条 `∃ G, Facts G [sat] [ref]` 定理，用 `decideFin!` 关闭」，本仓库 31 个文件就是这个形状。
> 附带说明它可能被拒的三类理由（与项目组织方式冲突、反例存在性并非新事实、生成文件维护成本），以及更可能被接受的替代形态。

---

Nothing in this section was done. It describes the work a merged contribution would
require, and the reasons it might not be accepted.

## 1. What "contribution" means in that project

ETP accepts Lean files that state and prove facts about the 4694 laws, in its own
layout:

- a `Magma` instance, usually from a literal table: `def «Name» : Magma (Fin n) where op := finOpTable "[[...]]"`;
- a theorem carrying `@[equational_result]` whose conclusion is
  `∃ (G : Type) (_ : Magma G) (_ : Finite G), Facts G [satisfied] [refuted]`;
- the proof discharged by `decideFin!` for finite witnesses;
- the file placed where the project's tooling expects it, and the whole project
  building under `lake build`, with CI green.

A contribution is what a maintainer merges after review. A repository that reproduces
the same statements is evidence, not a contribution.

## 2. The formalisation shape, if it were done

The 31 files in [`../lean/`](../lean/) are already in that shape, generated rather
than hand-written:

```lean
def «Refutation899» : Magma (Fin 9) where op := finOpTable "[[...]]"

@[equational_result]
theorem «facts Refutation899» : ∃ (G : Type) (_ : Magma G) (_ : Finite G),
    Facts G [168, 1486, 1487, 2126, 2164] [3462, …] :=
  ⟨Fin 9, «Refutation899», Finite.of_fintype _, by decideFin!⟩
```

Each `Facts` list is computed from the data, not copied from the upstream annotation:
the first list is the laws the table satisfies, the second the laws it refutes. That
matters, because copying the upstream `Facts` would reproduce exactly the defect this
work diagnoses.

What a real contribution would add on top of these files:

| Step | Status here |
|---|---|
| files in the project's directory layout, with its naming conventions | not done (they live in `lean/`, self-contained) |
| `lake build` of the whole project after adding them | **not done** |
| the project's CI | **not done** |
| a maintainer reviewing the `Facts` choices | **not requested** |
| removing duplication with facts already recorded in other files | not done — 206 of the 264 pairs are already separated by files whose annotation omits them |

## 3. Three reasons it might be rejected, in order of likelihood

These are judgements about what a maintainer would weigh, not measured facts.

**(a) The mathematical content is not new.** ETP already proves these pairs admit
finite counterexamples; that is what `finite_uncovered.txt` records. A contribution
that says "here are 264 tables" adds instances, not knowledge. A maintainer may
reasonably ask why the library should carry 264 more `Facts` entries whose content
follows from tables it already has.

**(b) It conflicts with how the directory is organised.** `Generated/All4x4Tables` is
a family of deliberately generated attempts, each recording what was attempted. A
reverse-index dump is organised by *what a table happens to satisfy*, which is a
different axis. It may belong in tooling or documentation rather than in the
statement library.

**(c) Maintenance cost.** 31 new files, three of them with 21- to 65-element tables,
generated by a script outside the project's toolchain. The project would have to
either adopt the generator or accept files it cannot regenerate.

## 4. What is more likely to be accepted

In descending order of plausibility, as a guess about reviewer taste:

1. **A tooling contribution to `parsimagma`, not to ETP.** The measurable defect is
   there: a corpus missing published tables, transposes, and a reverse query. The
   draft in [`../submission/pr_draft.md`](../submission/pr_draft.md) is shaped for
   that repository, including `src/` touch points and the tests to add.
2. **A correction to `finite_uncovered.txt`.** 16 of its 39 rows on the 1062 side are
   closed by `src/ext.rs` and the file was never regenerated. That is a bug report
   with a fix, independent of everything else here.
3. **A documentation note about the index.** The finding "`Facts` records what was
   emitted, not what is satisfied" is cheap to state and expensive to rediscover.
4. **The 31 Lean files**, if a maintainer wants the coverage and is content with
   generated files.

## 5. Preconditions, if someone does attempt it

- **Build the project fully.** `lake build` must pass, not just the witness files.
  Everything in [`06-boundaries.md`](06-boundaries.md) §2 stays true until it does.
- **Follow the naming and placement conventions exactly** — the project's own
  generator is the reference, not this repository.
- **Justify each `Facts` list.** With 206 silent witnesses, the interesting part is
  *why* a table satisfies laws its annotation omits; a reviewer will ask.
- **Open the conversation before the PR.** An issue describing the index defect, with
  the 264 pairs and the 31 tables as evidence, is a cheaper first step than 31 files.
- **Posting is a human decision.** Everything in [`../submission/`](../submission/) is a
  draft.

## 6. What the evidence covers

- 31 files typecheck individually; nothing is merged.
- The existence of the 264 finite counterexamples was already known — ETP proves it, and
  `finite_uncovered.txt` records it; the tables supply the witnesses.
- The corpus is incomplete in specific, measured ways: missing tables, missing
  transposes, and a query direction that was never asked.
- The 790 figure was not re-measured here; only the arithmetic around it was checked.
